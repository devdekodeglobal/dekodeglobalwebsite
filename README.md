# DEKODE Conversational Experience

This Vite/React application contains the existing DEKODE text conversation plus an optional, isolated real-time browser voice layer called **DEKODE Voice**.

## DEKODE Voice architecture

The integration point is `src/components/ChatApp.jsx`. With voice enabled, the existing microphone position opens `DekodeVoiceSession`; with voice disabled, the original speech-input handler and all existing text-chat behaviour remain in place. Completed voice turns are appended through the same `messages` collection, and voice knowledge responses are passed into the existing `CompanyKnowledgePanel`.

The implementation is separated into:

- `src/components/voice`: permission, listening, thinking, speaking, transcript, interruption, meeting preference, end state, and editable lead-review UI.
- `src/voice`: feature configuration, analytics allow-list, session state model, browser speech providers, intent classification, knowledge-grounded conversation, and lead qualification.
- `src/meetings`: replaceable meeting provider contract, dynamic mock provider, and calendar-provider placeholder.
- `src/leads`: editable form generation, validation, sanitised payload preparation, and mock/server notification adapter.
- `src/consent`: explicit consent state helpers.
- `api/leads.js` and the Sites worker generated by `scripts/prepare-sites-build.mjs`: server-side validation/sanitisation boundaries with truthful mock delivery.

Browser `SpeechRecognition`/`webkitSpeechRecognition` and `speechSynthesis` are development fallbacks, not a production realtime voice provider. If recognition is unavailable or permission is denied, the same voice session remains usable through its text field.

Raw audio is not permanently stored. Analytics events use an allow-list and exclude transcripts and personal project details.

## Configuration

Copy `.env.example` to `.env.local` when local overrides are needed:

```env
VITE_DEKODE_VOICE_ENABLED=true
VITE_VOICE_PROVIDER=browser
VITE_VOICE_FALLBACK_ENABLED=true
VITE_MOCK_MEETING_SLOTS_ENABLED=true
VITE_COMPANY_TIMEZONE=Asia/Kolkata
VITE_LEAD_NOTIFICATION_MODE=mock
VITE_LEAD_NOTIFICATION_ENDPOINT=/api/leads
```

All `VITE_*` values are public client configuration. Never place a voice, email, CRM, or calendar secret in them.

## Protected client proposals

The client-proposal feature is isolated behind `VITE_CLIENT_PROPOSALS_ENABLED`.
Approved proposal source is stored under `api/_proposal/source`, verified by
SHA-256, and converted into server-only response payloads during the build.
The public Vite bundle contains the generic renderer and access interface only.

Production requires a long, random `PROPOSAL_SESSION_SECRET` server variable.
Proposal access creates a signed, expiring, HTTP-only cookie scoped to one
proposal. Protected content, assets, and proposal chat reject requests without
that session and return private/no-store/noindex headers.

To intentionally update an approved proposal:

1. Replace the server-only source snapshot from the approved source repository.
2. Review the exact source diff.
3. Update the pinned source, diagram, and generated-content hashes in the build
   script and integrity test.
4. Increment the proposal version and record the approval metadata.
5. Run the full test and production-build suite.

To disable DEKODE Voice and retain the legacy microphone path:

```env
VITE_DEKODE_VOICE_ENABLED=false
```

## Google Calendar booking

The text and voice experiences share the same server-side Google Calendar integration. The browser requests safe availability data from `/api/calendar/availability`; `/api/calendar/book` rechecks the selected time before creating an event, Google Meet link, and attendee invitation.

Set these server-only values in Vercel and `.env.local`:

```env
GOOGLE_CALENDAR_ID=contactus@dekodeglobal.com
GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=
GOOGLE_REFRESH_TOKEN=
GOOGLE_CALENDAR_TIMEZONE=Asia/Kolkata
GOOGLE_CALENDAR_WORKDAY_START=09:00
GOOGLE_CALENDAR_WORKDAY_END=17:00
GOOGLE_CALENDAR_MEETING_DURATION_MINUTES=30
GOOGLE_CALENDAR_BUFFER_MINUTES=15
GOOGLE_CALENDAR_MINIMUM_NOTICE_HOURS=0
GOOGLE_CALENDAR_DAYS_TO_SEARCH=31
GOOGLE_CALENDAR_MAXIMUM_SLOTS=250
VITE_MEETING_PROVIDER=calendar
```

Enable the Google Calendar API in the Google Cloud project and generate the refresh token while signed in as `contactus@dekodeglobal.com`, with a Google Calendar OAuth scope. Keep all four `GOOGLE_*` credentials server-side, then redeploy after setting them in Vercel.

## Mock meeting slots

`MockMeetingSlotProvider` is active when `VITE_MEETING_PROVIDER=mock`. It:

- generates the next seven weekdays dynamically;
- excludes Saturday and Sunday;
- offers 11:00, 14:00, and 16:30;
- applies minimum booking notice;
- stores ISO timestamps;
- displays the visitor’s detected timezone; and
- marks every slot as mock development data.

The interface calls these values “preferred meeting times” and never claims a booking is confirmed.

Mock slots are preview-only and cannot create a calendar event.

## Connecting a production voice provider

Implement the existing speech/conversation provider contracts rather than coupling a vendor SDK to the UI:

1. Add secure server-side token/session routes for the selected provider.
2. Keep permanent credentials only in server runtime variables.
3. Implement `start`, `stop`, transcript callbacks, response events, and interruption behaviour matching the browser providers.
4. Select the provider through `VITE_VOICE_PROVIDER`; use only a public provider identifier in the browser.
5. Preserve the browser providers as the explicit fallback path.

## Lead delivery

The default `mock` mode validates and prepares a request but does not send email, create a CRM record, or book a meeting. The UI states this accurately.

To add real delivery, connect mail or CRM services inside `api/leads.js` (and the equivalent Sites worker/server handler), store credentials only on the server, and return `delivered: true` only after the external service confirms success.

## Development and verification

```bash
npm install
npm run dev
npm test
npm run lint
npm run build
```

`npm run dev` includes a development-only bridge for the existing `/api`
handlers, so password-protected proposals, proposal chat, protected assets, and
mock lead validation work from the Vite local URL. The bridge reuses the same
server handlers as the hosted API and uses the server-side
`PROPOSAL_SESSION_SECRET` when provided. When it is omitted locally, the
proposal security module supplies its existing development-only fallback; this
fallback is never permitted in production.

`npm run build` regenerates `src/knowledge/companyKnowledge.json` from the approved sibling `Dekode` company repository before compiling. Voice and text therefore use the same knowledge bundle loaded once at runtime.

## Current limitations

- Browser speech recognition support varies by browser and may use a browser-vendor speech service.
- Browser speech synthesis is not a low-latency production realtime voice implementation.
- Calendar booking requires Google OAuth credentials in the server environment; mock slots remain available for UI development.
- Lead delivery defaults to mock mode and does not send email.
- The current application has no authentication layer, so the consent-gated profile reuse adapter is implemented and tested but not connected to a logged-in UI.
- Conversational lead extraction is deterministic and intentionally conservative; every inferred form field remains editable.

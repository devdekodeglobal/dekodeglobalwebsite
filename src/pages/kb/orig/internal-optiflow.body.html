OptiFlow
Intelligent Inventory Allocation & Replenishment Engine

Automating physical optical inventory distribution for Centre For Sight (CFS) across 95+ retail clinics nationwide. Replaces 12,600+ annual spreadsheet hours with deterministic FIFO allocation math and Human-in-the-Loop exception approvals.

What OptiFlow Does

Transforms manual optical inventory distribution for retail chains like Centre For Sight (CFS) from 12,600+ annual spreadsheet hours into an automated, deterministic replenishment system with Human-in-the-Loop exception approvals.

Architectural Law: Closed Layers

Routers never call SQL directly; Services never touch raw DB sessions; Repositories isolate all database interactions. The API layer communicates only with the business service layer.

01

Discovery: Client Problem & Operational Context

Centre For Sight (CFS) operates a distributed nationwide retail network of optical stores across PAN India. Their entire physical inventory replenishment is supplied by a central logistics warehouse located in Dwarka, New Delhi.

Client Operational Baseline

The Dwarka warehouse serves as the central hub supplying 95+ retail store locations across three tiers:

  • 22 Grade A Stores: High velocity metropolitan flagships with weekly distribution cycles.
  • 30 Grade B Stores: Regional centers running on fortnightly replenishment schedules.
  • 43 Grade C Stores: Satellite clinics on monthly allocation cycles.

The Core Challenge

The logistical challenge is accurately calculating specific Planogram deficits at each store and determining exactly which frames or sunglasses (or acceptable substitutes) must be dispatched from Dwarka to maintain display compliance.

Because store managers cannot afford bare shelves, any replenishment delay directly degrades optical sales revenue.

OptiFlow transitions Centre For Sight from manual spreadsheet analysis to an automated, intelligent allocation workflow.

05

Deterministic Allocation Logic Flow & Rules Engine

At the heart of OptiFlow is the Deterministic Allocation Engine (backend/app/business/allocation_engine.py). It replaces subjective human spreadsheets with strict mathematical constraints and a tiered waterfall matching algorithm.

The Deficit Formula: Deficit = Target (Facing + Depth) - Store Stock On Hand (SOH). If Deficit > 0, the allocation waterfall begins.

Tier 1: Recent Sales Match

Fetches exact SKUs sold in the store over the lookback window (Last 7 Days). Verifies warehouse stock and allocates directly.

Tier 2: Historical Sales Match

If Tier 1 stock is unavailable, searches exact SKUs sold over the last 6 months to maintain customer brand affinity.

Tier 3: Substitute Cascade

If exact SKUs are exhausted, evaluates substitute frames within MRP ±20%, systematically relaxing Color → Material → Shape.

N-Tier Closed Layer Architecture & Corrected Boundary Rules

OptiFlow enforces a strict Closed Layered Architecture. Components at any given layer may only make calls into the layer directly beneath them. Layer skipping (such as an API controller making raw database queries or UI components querying tables directly) is strictly prohibited.

Architecture Boundary Clarification: The API Router layer communicates exclusively with the Business Service Layer. It never reaches directly into data repositories, underlying databases, or infrastructure layers. All data operations are mediated through typed domain services and transactional repositories.

Why Closed Layers?

Closed layering decouples presentation contracts from database structure. Changes to database normalization or indexing never leak into frontend payloads, and calculation engines can be tested in complete isolation using pure in-memory data structures without standing up databases.

Separation of Concerns

Routers handle HTTP status codes, headers, and parameter parsing. Domain services contain pure retail business logic (no HTTP concepts). Repositories contain SQL queries (no business rules).

Architecture Design Philosophy

1. The "Core Setup" is the Brain (Stores, Brands, Products):
These three tables act as the central brain. By storing csv_aliases directly inside the Stores and Products tables, the central engine translates raw POS/ERP exports without requiring human cleaning.

2. The "Rules" link the Brain (Planograms):
The Planograms table sits exactly in the middle of Stores and Brands. It uses a Composite Primary Key (store_code + brand_name + product_type), preventing duplicate or conflicting facing targets from ever being created.

3. Strict Flow Control (Stock, Sales, Allocations):
Because of foreign key cascade constraints, if a user uploads a Stock CSV for a store that doesn't exist in Stores (and doesn't match a stored alias), the database rejects the insertion and alerts the dashboard, ensuring dirty data never enters the math engine.

Data Versioning & Automated Audit Hooks

Retail allocation is legally and financially sensitive. OptiFlow captures full point-in-time state without requiring engineers to manually write logging code inside business routines.

Automated Delta Interceptor

Located in backend/app/data/listeners.py, this hook listens to SQLAlchemy's before_flush event on SessionLocal. It inspects all pending modifications: 

# backend/app/data/listeners.py
@event.listens_for(SessionLocal, 'before_flush')
def receive_before_flush(session, flush_context, instances):
    for obj in session.dirty:  # Intercepts updates
        state = attributes.instance_state(obj)
        old_state, new_state = {}, {}
        for col in obj.__mapper__.columns:
            attr = state.attrs.get(col.key)
            if attr and attr.history.has_changes():
                old_state[col.key] = _json_safe_val(attr.history.deleted[0])
                new_state[col.key] = _json_safe_val(getattr(obj, col.key))
        
        session.add(AuditLog(
            table_name=obj.__tablename__,
            record_key=str(obj.__mapper__.primary_key_from_instance(obj)),
            action_type="UPDATE",
            changed_by="system",
            old_state=old_state,
            new_state=new_state
        ))
Automatic Primary Key Detection: The listener handles composite primary keys (e.g. (store_code, brand_name, product_type) on Planograms) automatically via primary_key_from_instance.

Testing-First Approach, Frameworks & Live Test Suite Matrix

At DEKODE, OptiFlow is built using a Testing-First Paradigm. Tests are not retroactive paperwork written after a feature ships - they are the executable contract and safety net that enable rapid refactoring, confident AI-agent code generation, and zero regressions.

1. Shift-Left Contract Definition Design Phase

Before writing business logic, define the request/response schema, expected error states, and mathematical edge cases in test fixtures first.

2. Zero Silent Fallbacks Integrity

When a calculation or API endpoint fails, tests must assert that the system surfaces an explicit error state rather than silently falling back to stale mock data or null objects.

3. 100% Green Pre-Merge Gate CI Enforced

No pull request merges to develop or main without all backend unit/DAL/contract tests and frontend interceptor tests passing with 0 errors.

Code Quality, Dependency Auditing & Security Scanning

OptiFlow enforces automated code quality checks, static vulnerability analysis, and third-party dependency auditing across both Python and JavaScript ecosystems. No pull request may be merged with unresolved high-severity vulnerabilities.

Python Backend Quality & Security Auditing

  • Linter & Formatter: ruff check . and ruff format . (enforces PEP 8, import sorting, and syntax cleanliness).
  • Dependency Vulnerability Audit: pip-audit or safety check scans requirements.txt against the PyPA Advisory Database.
  • Static Code Security Analysis: bandit -r backend/app/ scans AST for SQL injections, unsafe yaml/pickle loads, and hardcoded credentials.
  • Type Safety: mypy backend/app/ checks type hinting and prevents runtime NoneType crashes.
pip-audit --desc on catches known CVEs in upstream packages before production deployment.

Frontend React Quality & npm Auditing

  • NPM Dependency Security Audit: npm audit --production detects known vulnerabilities across the node_modules tree.
  • Automated CVE Remediation: npm audit fix patches minor and patch semver vulnerabilities without breaking contracts.
  • Linting: eslint src/ checks React hooks rules (preventing stale closure and infinite re-render loops).
  • Defensive Type Coercion: Always coerce numerical values with Number(val) || 0 to prevent NaN cascading errors in charts.
Zero tolerance for unreviewed npm audit critical vulnerabilities in production bundles.

Security & Authentication Subsystem

OptiFlow employs stateless JWT Bearer token authentication with bcrypt password encryption.

JWT Token Workflow

  1. Client posts credentials to /api/v1/auth/token (x-www-form-urlencoded).
  2. Backend validates credentials against bcrypt hash in app.config or user store.
  3. Returns signed JWT token with configurable expiry (default: 60 minutes).
  4. Client includes header Authorization: Bearer <token> on requests.

FastAPI Dependency Injection

Endpoints enforce authentication using standard FastAPI dependencies: 

from app.common.security import get_current_user

@router.get("/protected")
def my_endpoint(user: str = Depends(get_current_user)):
    return {"authenticated_as": user}

Developer Recipe: Adding a New API Endpoint

To preserve closed-layer discipline, never write database queries directly inside an API router. Follow this 4-step pipeline when introducing a new feature:

Step 1 Define Pydantic DTO Schemas backend/app/common/

Create typed request and response schemas isolating API contracts from database schema:

# app/common/store_dto.py
from pydantic import BaseModel

class StorePerformanceResponse(BaseModel):
    store_code: str
    fill_rate_percentage: float
    unmet_deficit_units: int
Step 2 Implement Data Access Repository backend/app/data/repositories/

Encapsulate all SQLAlchemy queries inside the DAL repository layer:

# app/data/repositories/store_repository.py
def get_store_metrics(self, store_code: str):
    return self.session.query(Allocation).filter(Allocation.store_code == store_code).all()
Step 3 Implement Domain Business Service backend/app/business/

Execute retail business logic, compute statistics, and return typed DTOs without touching HTTP status codes:

# app/business/store_service.py
class StoreService:
    def calculate_metrics(self, store_code: str) -> StorePerformanceResponse:
        with get_db_context() as db:
            repo = StoreRepository(db)
            records = repo.get_store_metrics(store_code)
            # Compute retail formulas and return DTO
            return StorePerformanceResponse(...)
Step 4 Mount Router in API Layer & Register in Service Host backend/app/api/

Expose the endpoint in app/api/ and register in app/main.py with dependency-injected auth:

# app/api/stores.py
@router.get("/{store_code}/metrics", response_model=StorePerformanceResponse)

Issue: "Zero In-Hand Units" Displayed in UI

Root Cause: User selected a historical snapshot run (e.g., from an early PoC run) where stock columns were unpopulated.

Resolution: Switch the run selector at the top of the screen to the latest active run, or trigger a new run via the "New Allocation" modal. The backend automatically populates facing, current_soh, back_stock, and initial_gap on all modern runs.

curl -H "Authorization: Bearer <token>" \

Returns detailed old_state and new_state JSON diffs showing who modified planogram facings and when.

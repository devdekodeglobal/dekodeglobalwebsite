Core Engineering Principles

1. Closed-Layer Discipline Structure

No layer skipping. API controllers parse HTTP and delegate to business services. Business logic performs calculations and delegates persistence to data access repositories. UI never touches databases directly.

2. Zero-Destructive Deletions Data Safety

Avoid hard SQL DELETE calls on business records. Use soft-delete flags (is_deleted) and immutable versioned runs (run_id snapshots) to maintain historical auditability.

3. Defensive Data Fallbacks Resilience

Assume all third-party API and database numerical fields could be null. Coerce numbers cleanly (Number(val) || 0) to prevent NaN cascading or zero-division crashes in UI charts.

The DEKODE Rule: Code readability, maintainability, and domain correctness always trump clever one-liners. If an architecture requires an explanation in Slack, it must be documented in the repository's docs/ folder first.

SOLID & Clean Architecture Principles

To prevent codebase rotting and high refactoring costs as projects scale, all backend services and frontend stores must respect the 5 SOLID tenets:

SSingle Responsibility SRP

Each class, module, or hook must have exactly one reason to change.

  • Bad: An API router that handles HTTP parsing, executes matrix mathematics, and performs SQL commits.
  • Good: Router delegates to AllocationService, which invokes AllocationRepository.

OOpen / Closed OCP

Software entities must be open for extension, but closed for modification.

  • Application: Introduce new calculation strategies or match tiers via strategy interfaces/handlers without modifying existing verified matching loops.

LLiskov Substitution LSP

Derived classes or repository implementations must be substitutable for their base contracts.

  • Application: In-memory test SQLite repositories must behave identic to PostgreSQL production repositories without unexpected side effects.

IInterface Segregation ISP

Clients must not be forced to depend on interfaces they do not use.

  • Application: Split bloated 1000-line repositories into focused domain repositories (e.g. StoreRepository, StockRepository, AuditRepository).

DDependency Inversion DIP

Depend upon abstractions (interfaces / protocols), not concrete implementations.

  • Application: In FastAPI and Go, pass database sessions, configurations, and logger instances via dependency injection, allowing trivial test harness mocking.

Auditing, Provenance & Immutable History Standard

At DEKODE, systems handle critical operations, inventory movements, compliance checkpoints, and financial figures. Auditing is never an afterthought or an optional toggle. Every data mutation must be cryptographically traceable, non-destructive, and automatically recorded.

ORM Mutation Trigger → before_flush Hook → Delta Extractor (Old vs New) → audit_logs Table (Immutable)

1. Automated Delta Tracking SQLAlchemy Hooks

Mutations are intercepted at the ORM session level before flushing. Handlers extract exact previous and current field states (old_state vs new_state) without requiring developers to manually write audit inserts in every route.

  • Captures INSERT, UPDATE, and DELETE.
  • Records changed columns, user attribution, and UTC timestamps.
  • JSON-serializable representation for all numeric and datetime datatypes.

2. Immutable Run Versioning Zero Overwrite

Algorithmic outputs (such as inventory allocations, schedule runs, or AI prompts) must never overwrite previous outputs in-place.

  • Each run creates a unique, immutable run_id (UUID4).
  • All generated rows reference that specific run_id.
  • Historical calculations remain fully reproducible and auditable for audits and stakeholder post-mortems.

3. Zero-Destructive Deletions Soft Delete Only

Direct DELETE FROM statements on operational or transactional tables are strictly banned.

  • Entities employ a boolean is_deleted flag with an index.
  • Repository queries filter active records with is_deleted = False.
  • Preserves referential foreign key integrity and enables instant data recovery.

DEKODE Audit Log Schema Standard (PostgreSQL & SQLite)

Every project repository implementing persistent storage must include an audit_logs table matching or extending this standard contract:

class AuditLog(Base):
    __tablename__ = "audit_logs"

    id = Column(Integer, primary_key=True, autoincrement=True)
    table_name = Column(String(64), nullable=False, index=True)
    record_key = Column(String(128), nullable=False, index=True)
    action_type = Column(String(16), nullable=False)      # INSERT | UPDATE | DELETE
    changed_by = Column(String(128), default="system")
    changed_at = Column(DateTime, default=datetime.utcnow, nullable=False)
    old_state = Column(JSON, nullable=True)                 # JSON snapshot before mutation
    new_state = Column(JSON, nullable=True)                 # JSON snapshot after mutation
Proven in OptiFlow: The OptiFlow backend automatically records all store modifications via backend/app/data/listeners.py (using SQLAlchemy's receive_before_flush event listener), verified by automated unit tests in tests/dal/test_transactions.py and tests/dal/test_versioning_audit.py.

UI Design: High Readability & Minimalist UX

When designing user interfaces for internal enterprise apps or client portals, engineers must prioritize instant legibility, low cognitive fatigue, and clean minimalism:

1. High Typography Contrast Readability

Avoid low-contrast gray text on dark backgrounds. Use clean sans-serif typefaces (Inter) with at least 4.5:1 WCAG contrast ratios. Never use font sizes below 12px for data tables.

2. Progressive Disclosure Minimalism

Do not overwhelm users with 50 filters on page load. Present summary KPIs first, standard filters second, and nest technical raw details inside collapsibles or drawer modals.

3. Responsive First (Mobile & Tablet) Adaptability

Internal tools are frequently checked on iPads and mobile phones by store managers. Ensure tables scroll horizontally with sticky first columns, and cards collapse into single columns without text truncations.

The "No Clutter" Rule: White space is not wasted space. Generous padding (16px-24px) around cards and concise labels make complex retail metrics intelligible at a glance.

Before Anyone Builds: The 6 Pre-Build Documents Gate

Building software with AI is fast now - and that is the trap. When code generation takes minutes, teams skip upfront decisions, leaving critical architecture choices to whoever is typing prompts. You only find out what was chosen when you inspect broken code.

The DEKODE Pre-Build Law: "Decide on paper, then build, and you only pay for the application once." Every new system, client portal, or feature epic must have these 6 documents written, reviewed, and signed off before a single page of code gets written.
1

Product Requirement Document (PRD)

What it does

Every feature listed in plain words. Who uses it, what they are trying to accomplish, and what counts as finished. If a feature isn't on this list, it isn't in the build.

Covers
Features, personas, user stories, acceptance criteria ("Done").
Without It
The software does what the builder or AI guessed you meant.
2

Technical Requirements Document (TRD)

The tools it runs on

What the application runs on, where it is hosted, and which existing systems it talks to. Decided once, written down, so nobody guesses or swaps frameworks halfway through.

Covers
Platform, hosting, dependencies, APIs, and rate limits.
Without It
Tools get swapped mid-build, libraries conflict, work gets redone.
3

App Flow & User Journey Map

What clicks do

The exact path a visitor or client takes, screen by screen. Which page comes next, what happens when a form submits, and where someone lands when an error occurs.

Covers
Every screen transition, state change, and fallback dead-end.
Without It
Dead ends nobody notices until a live client hits one in prod.
4

Design Brief & UI System

How it looks

Your colours, fonts, logo usage, and how buttons, headings, tables, and forms look across viewports. It keeps the tenth screen as cohesive and on-brand as the first.

Covers
Palettes (DEKODE Navy/Gold), typography, tokens, components.
Without It
A Frankenstein interface that looks like five different templates.
5

Database Schema & Access Controls

NEVER SKIP · DATA SAFETY

What data gets stored, where it sits, and who on your team or client list is authorized to see each field. This is the document that protects your clients and company.

Covers
Entities, relations, migrations, provenance columns, and RBAC rules.
Without It
Data leaks. Nobody can guarantee who can access client records.
6

Implementation & Staging Plan

What builds in what order

The build broken into discrete phases, with concrete deliverables and client/lead sign-off gates before subsequent phases start.

Covers
Stages, milestones, tests required per stage, sign-off checkpoints.
Without It
Everything stays "nearly done" for weeks with no clear finish line.

AI Feedback Loops & Engineering Protocols

AI coding assistants (Claude Code, Antigravity, Cursor, Copilot) are powerful accelerators, but unfocused prompting leads straight into the Doom Loop. At DEKODE, all AI-assisted engineering follows two strict dual-review feedback loops:

Loop 1 · Design Phase
Plan → Review → Fix

Iterate in markdown, never in code. Spec the layers and review before generating a single line.

Loop 2 · Build Phase
Implement → Review → Fix

Build in fresh context. Review for error states, test coverage, and security before merging.

Debugging Golden Rule
Diagnose ≠ Fix

Never let a stuck agent thrash in code. Spawn a clean subagent: "Just diagnose and report back, do not touch code."

1. Iterate in Markdown, Not Code Planning

Changing requirements in code is expensive and introduces technical debt that confuses future agents. Spec out schemas, edge cases, and endpoints in markdown first until aligned.

2. Fresh Context & Context Rot Hygiene

Long sessions suffer from context rot and inherited biases. Break work into small, scoped batches. Reset sessions or spin up fresh agents when transitioning from planning to implementation.

3. Verification Loops & Zero Secrets Quality

Run pytest, npm test, and npm run build immediately after generation. Never prompt agents with real production secrets, API keys, or customer PII.

The "Doom Loop" & AI Anti-Patterns to Avoid

The AI Doom Loop occurs when an agent says it fixed a bug, but the bug persists, and subsequent prompts create thrashing and regressions across layers.

Data Layer (DB / Schema) ↔ Controller Layer (Services / Logic) ↔ View Layer (React / UI State) Must Stay 100% In Sync

[X] The Three-Layer Desync Trap

Symptom: UI requirements change, but the agent only tweaks the frontend component while leaving the backend model or API contract out of sync.

Remedy: Always require agents to update and verify all 3 layers: Database → Service/Controller → View.

[X] The "Blind Thrashing" Trap

Symptom: Letting an agent keep attempting guesses on a complex bug, accumulating messy patches and phantom dependencies.

Remedy: Kill the thrashing loop. Revert unverified changes and prompt a fresh agent to diagnose root cause only.

[X] The "Layer Skipping" Trap

Symptom: Agent writes raw SQL queries directly inside FastAPI route handlers or frontend components.

Remedy: Strictly enforce our Closed-Layer pattern: Router → Service → Repository (DAL).

Testing-First Engineering & Quality Gates

At DEKODE, we operate with a Testing-First Approach. Tests are not retroactive paperwork written after a feature ships - they are the executable contract and safety net that enable rapid refactoring, confident AI-agent code generation, and zero regressions.

1. Shift-Left Contract Definition Design Phase

Before writing business logic, define the request/response schema, expected error states, and mathematical edge cases in test fixtures first.

2. Zero Silent Fallbacks Integrity

When a calculation or API endpoint fails, tests must assert that the system surfaces an explicit error state rather than silently falling back to stale mock data or null objects.

3. 100% Green Pre-Merge Gate CI Enforced

No pull request merges to develop or main without all backend unit/DAL/contract tests and frontend interceptor tests passing with 0 errors.

1. Contract Fixtures → 2. Math & DAL Units (Pytest) → 3. API Client Interceptors (Vitest) → 4. CI Pre-Merge Gate (100% Green)

Branch Management & Team Showcase Workflow

We practice a protected Git Flow across 3 mainline branches. No developer commits directly to main or staging.

develop Active Integration

Where all approved feature branches land. Deployed automatically to the internal development sandbox.

staging Client UAT & Preview

Where releases are tested before production. Used for internal showcases and client demos.

main Production Truth

100% verified, production-ready code. Triggers continuous deployment to live servers.

The Showcase Protocol: How to Present Work Before Production

1
Create Feature Branch

Branch off develop using clean naming: feat/store-deficit-clustering or fix/nan-table-export.

2
Run Verification Suite Locally

Run pytest, npm test, and npm run build. All must pass cleanly with 0 warnings.

3
Prepare Showcase Artifacts

Record a 60-second Loom/WebM demo or capture before-and-after screenshots. Attach them directly to the Pull Request description.

4
PR Review & Staging Deploy

Once CI passes and the team approves the PR, code merges into develop and deploys to staging for stakeholder testing.

5
Production Promotion to main

After stakeholder sign-off on staging, a fast-forward release PR merges into main.

Conventional Commit Standards

All commits must follow the Conventional Commits specification to enable automated changelogs and clean history: 

<type>(<scope>): <subject>

[optional body]
[optional footer(s)]

Allowed Types

  • feat: New user-facing feature or API endpoint.
  • fix: Bug fix in code or algorithm.
  • perf: Performance optimization (bundle splitting, index addition).
  • test: Adding or updating test suites.
  • docs: Documentation, diagrams, or handbook edits.
  • refactor: Code restructure without changing behavior.

Examples

  • feat(backend): add store-level deficit clustering endpoint
  • fix(frontend): resolve NaN calculation in drill-down cards
  • perf(frontend): split vendor chunks for charts and react
  • test(dal): add transactional rollback verification
  • docs: add company engineering standards handbook

Security & Zero Secrets Policy

Absolute Zero Tolerance: Never commit passwords, private keys, JWT secrets, or production connection strings to Git. Use .env.example with dummy placeholder strings only.

1. JWT Authentication

All non-public endpoints require Bearer JWT validation. Frontends must cleanly clear tokens and redirect to login on 401 Unauthorized.

2. Password Hashing

Always use passlib[bcrypt] or standard bcrypt algorithms with appropriate salt work factors. Plaintext passwords must never hit the database.

3. Audit Logging

Sensitive table mutations must be intercepted (via SQLAlchemy listeners or database triggers) and written to immutable audit_logs with old and new JSON states.

Observability, Logging & Alerting

If we cannot see a system, we cannot be accountable for it. Every service ships with logs, health checks, error tracking, and a small set of alerts before it reaches staging.

Request ID Created → Structured JSON Log → Error Tracker + Metrics → Actionable Alert

1. Structured Logs Logging

One JSON object per line to stdout. No print() or console.log in committed backend code.

  • Required fields: timestamp (UTC), level, service, request_id, message.
  • Add run_id and user_id (opaque ID) where relevant.
  • Levels: ERROR needs human action, WARN is recoverable, INFO is business events, DEBUG is off in production.
{"timestamp":"2026-01-01T00:00:00Z","level":"INFO","service":"optiflow-api",
  "request_id":"req_01H…","user_id":"u_opaque_123","message":"allocation run started"}

2. Never Log These Safety

Logs are copied to many systems and kept for a long time. Treat them as semi-public.

  • Passwords, tokens, API keys, session cookies.
  • Full request bodies containing customer data.
  • Personal data beyond an opaque ID (email, phone, address).

3. Health & Errors Runtime

Every service exposes two endpoints and reports unhandled exceptions to an error tracker (e.g. Sentry).

  • /healthz: process is alive. No dependency calls.
  • /readyz: database and required upstreams reachable.
  • Error events carry request_id and release version.
Signal Measure Default Alert
Rate Requests per second per endpoint Sudden drop to near zero
Errors 5xx ratio, unhandled exceptions Sustained 5xx above agreed threshold
Duration p50 / p95 / p99 latency p95 above agreed SLO
Jobs Batch / allocation run duration and failures Any failed or overdue scheduled run
Alert Hygiene Rule: Every alert must have an owner and a linked runbook. An alert nobody acts on gets tuned or deleted within one sprint.

Incident Response, Hotfix & Rollback

Production will break eventually. The standard is how fast we restore service and how well we learn. Roll back first, diagnose second.

Severity Definition Response
SEV1 Outage, data loss or exposure, or core workflow unusable for all clients. Immediate. Incident lead named. Client notified with regular updates.
SEV2 Major feature degraded or a subset of clients affected, workaround exists. Same business day. Owner assigned.
SEV3 Minor defect, cosmetic or low impact. Normal backlog.

Hotfix Flow

1
Stabilize: Roll Back

Redeploy the last known-good release (or disable the feature flag). Do not debug live while users are down.

2
Branch from main

Create hotfix/<short-description> from main. Add a failing test that reproduces the bug first.

3
Fast-Track PR

One reviewer minimum, full CI gate still applies. Merge to main and tag the release.

4
Back-Merge

Merge the hotfix into develop (and staging if diverged) the same day so the fix is not lost.

5
Blameless Post-Mortem

For SEV1 and SEV2, publish a short write-up in docs/incidents/ within five working days: timeline, root cause, what went well, and owned follow-up actions.

Rollback Readiness: Every release must be reversible. Database migrations follow expand / contract so the previous app version still runs against the new schema.

Backups & Recovery Restore-Tested

  • Production databases have automated backups and point-in-time recovery where the platform supports it.
  • Each project documents its RPO (max acceptable data loss) and RTO (max acceptable downtime) in the TRD.
  • A backup is not real until restored: run a restore drill into a scratch environment at least quarterly and record the result.

Privacy, Data Handling & Compliance

Scope note: DEKODE operates in Australia and India and handles client data across both. This section sets engineering defaults. It is not legal advice; have counsel confirm obligations under the Australian Privacy Act 1988 (including the Notifiable Data Breaches scheme) and India’s Digital Personal Data Protection Act 2023 and its rules, which are being phased in.

1. Data Minimization Collect Less

Only collect fields the PRD justifies. Every personal-data column in the schema doc (Doc 5) records its purpose, owner, and retention period.

2. Classification Know What You Hold

  • Public: marketing content.
  • Internal: business data, non-personal.
  • Confidential: client data, personal data.
  • Restricted: credentials, financial, government IDs, health.

3. Protection Defaults

  • TLS in transit, encryption at rest for databases and backups.
  • Mask or synthesize personal data in dev, test, and demo environments.
  • Choose data region deliberately and record it in the TRD.
Retention & Deletion vs. Soft-Delete - Reconcile: Our no-hard-delete rule supports audit history, but privacy law can require erasure or de-identification.
  • Soft-delete is the default for business records.
  • Personal data must have a documented purge or anonymization path once retention expires or a valid erasure request is approved.
  • Audit logs store opaque IDs and changed field names where possible, not raw personal values.

Authentication, Sessions & RBAC

Doc 5 says who may see which field. This section is how we enforce it. Authorization is checked on the server, in the service layer, on every request. Hiding a button in the UI is not access control.

Request + Token → Authenticate (who) → Authorize (may they) → Service + Audit Log

1. Tokens & Sessions JWT

  • Short-lived access tokens (minutes, not days).
  • Refresh tokens rotate on use and are revocable server-side.
  • Prefer HttpOnly; Secure; SameSite cookies over localStorage for browser apps, with CSRF protection when cookies are used.
  • Pin the signing algorithm; reject alg: none. Validate exp, iss, aud.

2. Role Model Least Privilege

  • Deny by default. Endpoints without an explicit permission check fail.
  • Roles map to permissions (e.g. stock:read, allocation:run); code checks permissions, not role names.
  • Enforce tenant / store scoping in repository queries, not only in routes.
  • Admin actions require re-authentication or MFA.

3. Hardening Baseline

  • Rate-limit login and token endpoints; lock out or slow repeated failures.
  • Explicit CORS allowlist, never * with credentials.
  • Security headers: Content-Security-Policy, X-Content-Type-Options, Strict-Transport-Security.
  • Generic login errors that don’t reveal whether an account exists.

Required Authorization Tests CI Enforced

For every protected endpoint, the contract suite asserts all three outcomes:

no token                               -> 401
valid token, wrong role / wrong tenant -> 403
valid token, correct role              -> 2xx
Review Trigger: Any change to roles, permissions, token handling, or a row-level scoping rule needs a security-focused reviewer and an updated Database Schema & Access Controls document.
